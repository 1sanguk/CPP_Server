# 깨달은 점 (버전별 학습 노트)

버그를 고치거나 개념을 짚으면서 실제로 이해하게 된 포인트를 남긴다. 버그 자체의 재현/수정 절차는 [troubleshooting.md](troubleshooting.md)에, 여기는 "왜 그런지"에 대한 개념 정리 위주.

## v1 — 싱글 스레드 blocking TCP 서버

- **POSIX API는 예외(exception)가 아니라 리턴값으로 에러를 알려준다.** `socket()`/`bind()`/`listen()`/`accept()` 등을 `try/catch`로 감싸는 건 의미가 없음 — 실패하면 음수를 리턴할 뿐 예외를 던지지 않는다. 항상 반환값을 직접 `if`로 체크해야 함.

- **함수의 리턴값이 항상 "저장할 가치가 있는 데이터"는 아니다.** `socket()`은 성공 시 실제로 쓸 fd를 리턴하지만, `bind()`/`listen()`은 성공/실패(0/음수)만 알려줄 뿐이라 그 값을 멤버 변수에 대입하면 오히려 기존 값을 덮어쓰는 버그가 됨

- **리스닝 소켓과 클라이언트 소켓은 서로 다른 fd이고 생명주기도 다르다.** 클라이언트 연결을 정리할 때 실수로 리스닝 소켓(`this->fd`)을 닫으면, 그 이후 `accept()`가 전부 실패해서 사실상 서버가 죽어버림. 리스닝 소켓은 서버 프로세스가 끝날 때(소멸자)만 닫아야 하고, 클라이언트 소켓은 그 클라이언트와의 연결이 끝날 때마다 닫아야 함.

- **`accept()`의 클라이언트 주소 구조체는 input이 아니라 output이다.** `bind()`에 쓰는 주소 구조체(내가 원하는 바인딩 주소를 알려주는 input)와 헷갈리기 쉬운데, `accept()`의 구조체는 커널이 "누가 접속했는지"를 채워주는 output이라 호출 전에 미리 값을 넣어봤자 의미가 없음.

- **`accept()`/`recv()`는 진짜로 스레드를 멈춘다(blocking).** CPU를 쓰면서 반복 확인(polling)하는 게 아니라, 커널이 "할 일이 생길 때까지 이 스레드는 깨우지 마"라고 완전히 재워버림. 그래서 한 클라이언트를 처리(특히 `recv()`에서 대기)하는 동안 다른 클라이언트의 접속 요청은 커널의 backlog 큐에 쌓이기만 하고 처리되지 않음 — 두 개의 `nc`를 동시에 열어서 직접 확인함(첫 연결 종료 후에야 두 번째가 응답받음).

- **자원(fd)을 직접 들고 있는 클래스는 복사(copy)에 취약하다 (Rule of Three).** 지금은 문제가 되지 않지만, 객체가 복사되면 같은 fd를 두 객체가 각자 `close()`하려는 이중 close 버그로 이어질 수 있음 — v2에서 스레드로 객체를 넘기게 될 때 다시 짚기로 함.

## v2 — thread-per-connection

- **비정적 멤버 함수의 주소는 반드시 `&ClassName::MemberFunc`처럼 스코프를 명시해야 한다.** 멤버 함수 본문 안에서는 다른 멤버 함수 이름을 그냥 써도 호출은 되지만, `std::thread`에 넘기듯 그 "주소"를 값으로 만들려는 순간에는 이름만으로 부족하다 — 컴파일러가 어떤 클래스의 멤버인지 판단할 근거가 없기 때문. `thread t(Process_Client, this, fd)`가 아니라 `thread t(&ThreadPerConnectionEchoServer::Process_Client, this, fd)`로 써야 함.

- **`recv()`로 채운 버퍼는 널 종료가 보장되지 않는다.** 문자열처럼 로그에 찍고 싶으면 `std::string(buffer, recv_result)`처럼 유효한 길이를 명시해서 감싸야 한다. 그냥 `cout << buffer`로 찍으면 이전 반복의 잔여 데이터나 초기화되지 않은 값 때문에 쓰레기 문자가 더 찍히거나, 최악의 경우 배열 범위를 넘어 읽는 UB로 이어질 수 있음.

- **`detach()`는 스레드 수명 관리를 포기하는 대신 구현을 단순하게 만드는 트레이드오프다.** thread-per-connection처럼 스레드가 일회성이면 detach로 충분하지만(스레드가 알아서 끝남), v3의 고정 크기 thread pool처럼 스레드를 미리 만들어 재사용하는 구조에서는 서버 종료 시 각 워커를 안전하게 멈추고 `join()`으로 정리하는 과정이 반드시 필요해진다.

## v3 — 고정 크기 thread pool + bounded 작업 큐

- **`condition_variable::wait()`는 mutex를 계속 잡고 잠드는 것이 아니다.** 대기하는 동안
  mutex를 풀어 생산자가 큐에 작업을 넣을 수 있게 하고, 깨어난 뒤 mutex를 다시 획득한
  상태에서 predicate를 확인한다. 그래서 작업 큐의 확인과 pop을 하나의 임계 영역으로
  유지할 수 있다.

- **중첩된 반복문이 많다고 시간복잡도가 자동으로 커지는 것은 아니다.** worker의 바깥
  반복문은 다음 작업을 기다리는 수명 주기이고, 안쪽 `recv()` 반복문은 현재 연결 하나의
  메시지를 처리한다. 두 반복의 입력 크기를 곱해 전부 순회하는 구조가 아니므로 코드의
  중첩 깊이만 보고 `O(n²)`로 판단할 수 없다.

- **고정 thread pool은 스레드 수를 제한하지만 대기 작업 수까지 제한하지는 않는다.**
  별도의 최대 큐 크기가 없으면 worker보다 빠르게 연결이 들어올 때 fd가 계속 누적된다.
  v3에서는 큐를 128개로 제한하고 초과 연결을 닫는 정책을 적용했다.

- **종료 상태만 바꿔서는 blocking 시스템 호출이 자동으로 끝나지 않는다.** worker의
  `recv()`는 client 소켓 `shutdown()`으로 깨웠고, macOS에서 listen 소켓 `shutdown()`만으로
  `accept()`가 풀리지 않는 경우에는 non-blocking listen fd와 timeout이 있는 `poll()`로
  종료 상태를 다시 확인하도록 구성했다.

- **주기 작업도 종료 알림을 받을 수 있어야 한다.** monitor가 `sleep_for(30초)`를 사용하면
  종료 직후에도 최대 30초 동안 join을 기다린다. 같은 condition variable의 `wait_for()`와
  종료 predicate를 사용하면 평상시 주기는 유지하면서 `notify_all()`에는 즉시 반응한다.

- **signal handler에서 일반 C++ 동기화 코드를 직접 호출하면 안 된다.** mutex와
  condition variable 조작은 async-signal-safe하지 않으므로 SIGINT/SIGTERM을 막은 뒤
  main 스레드의 `sigwait()`에서 동기적으로 받아 `Stop()`을 호출했다.

## v4 — Linux epoll 기반 단일 스레드 reactor

- **fd는 현재 프로세스 안에서 열린 자원을 가리키는 번호이며, client fd는 임시 연결 id처럼
  사용할 수 있다.** listen fd는 새 접속을 받는 문지기 소켓이고, client fd는 이미 연결된
  클라이언트와 실제로 `recv()`/`send()`하는 소켓이다. 그래서 `event_fd == listen_fd`이면
  `accept()`, 그 외 client fd이면 `recv()`로 분기한다.

- **`epoll_wait()`는 “이번에 준비된 fd 목록”을 돌려준다.** listen fd에 새 접속이 남아 있는데
  `accept()`로 소비하지 않으면 같은 listen 이벤트가 계속 발생하고, client fd에 읽을 데이터가
  남아 있는데 `recv()`로 소비하지 않으면 같은 client 이벤트가 반복된다.

- **`epoll_ctl()`의 첫 번째 인자는 감시자인 `epoll_fd`, 세 번째 인자는 감시 대상 fd다.**
  client fd를 등록할 때 `epoll_ctl(client_fd, ...)`처럼 쓰면 `Invalid argument`가 발생한다.
  올바른 의미는 `this->epoll_fd`의 감시 목록에 `client_fd`를 추가하는 것이다.

- **`eventfd`는 `epoll_wait()`를 깨우기 위한 fd로 사용할 수 있다.** `stopping` 같은 메모리
  변수만 바꿔서는 커널 안에서 잠든 `epoll_wait()`를 즉시 깨우지 못한다. `Stop()`이
  `stop_event_fd`에 값을 write하면 epoll이 stop 이벤트를 돌려주고, 이벤트 루프는 값을
  read한 뒤 종료한다.

- **정리 함수는 여러 번 호출되어도 안전해야 한다.** `Server_Run()` 종료와 소멸자 경로에서
  cleanup이 중복 호출될 수 있으므로 `cleaned_up` 플래그로 fd close와 로그가 한 번만
  수행되도록 했다.

- **Docker 컨테이너의 localhost와 macOS의 localhost는 다르다.** 컨테이너 안의 서버에
  macOS 터미널에서 접속하려면 `docker run -p 9000:9000 ...`처럼 포트 매핑이 필요하다.

## v5 — 이벤트 루프 + 워커 스레드 풀

- **non-blocking 소켓에서 `EAGAIN`은 `recv()`뿐 아니라 `send()`에서도 정상 신호다.**
  커널 송신 버퍼가 가득 차서 당장은 못 보낸다는 뜻이지, 연결이 끊기거나 진짜 오류가
  난 게 아니다. `Send_All()`이 이 경우를 에러로 처리하면 정상적인 백프레셔 상황에서도
  클라이언트를 끊어버리게 된다 — "몇 바이트를 보냈는지"까지 호출한 쪽에 돌려줘서 나머지를
  버퍼에 남겨두고 다음 기회에 이어 보내야 한다.

- **`epoll_ctl(EPOLL_CTL_MOD)`는 기존 이벤트에 추가하는 게 아니라 통째로 덮어쓴다.**
  `EPOLLIN`만 감시하던 fd에 `EPOLLOUT`을 "추가"하려면 `EPOLLIN`을 빼고 `EPOLLOUT`만
  넘기면 안 되고, `EPOLLIN | EPOLLOUT`을 같이 넘겨야 한다. 안 그러면 그 fd는 더 이상
  `EPOLLIN`을 못 받아 클라이언트가 다음 메시지를 보내도 서버가 못 알아챈다.

- **`std::mutex`는 재귀적으로 잠글 수 없다.** 어떤 락을 쥔 스코프 안에서 다른 함수를
  호출할 때, 그 함수가 같은 락을 다시 잠그려 하면 그 자리에서 멈춘다(데드락). 워커가
  `send_mutex`를 쥔 채로 `Delete_Client_Fd()`(내부에서 `send_mutex`를 또 잠그는 함수)를
  호출해서 두 번 겪었다 — 락 스코프 밖으로 호출을 빼거나, 상태만 플래그로 남겨뒀다가
  락이 풀린 뒤에 호출해야 한다.

- **람다는 캡처 목록에 적은 것만 쓸 수 있다.** `[this]`로 캡처하면 멤버 접근은
  되지만, 그 함수의 지역 변수(파라미터 포함)는 캡처 목록에 따로 적지 않으면 람다
  안에서 못 쓴다. `Worker_Loop(int index)`의 `wait()` predicate 람다에서 `index`를
  안 쓰고 `[this]`만 캡처해서 컴파일 에러가 났다 — `[this, index]`로 명시해야 했다.

- **여러 스레드가 로그를 찍을 때, 한 줄을 여러 번의 출력 호출로 나누면 뮤텍스를
  매번 걸어도 소용없다.** `cout << a; cout << b; cout << endl;`처럼 나뉘어 있으면
  그 사이사이에 다른 스레드가 끼어들 수 있다. 한 줄 전체를 문자열로 완성한 뒤
  단 한 번의 락 구간 안에서 통째로 출력해야 실제로 안 섞인다.

- **부하 테스트에서 나온 이상 현상이 항상 서버 코드의 버그는 아니다.** 부하 테스트
  중 재현된 "연결 실패"를 조사해보니 서버 로직이 아니라, 서버 프로세스를 감싼
  테스트용 `timeout` 값이 실제 테스트 소요 시간과 거의 같아서 우연히 종료 타이밍이
  겹친 테스트 하네스 문제였다. 재현 조건(타임아웃 여유, 부하 패턴)을 하나씩 바꿔가며
  원인이 서버 쪽인지 테스트 쪽인지 좁혀야 한다.

- **graceful shutdown에서 pending 데이터를 처리하는 데는 "무한정 기다리기"와 "그냥
  버리기" 사이에 현실적인 중간 지점이 있다.** `Clean_Up()`이 종료 시 각 연결의 남은
  송신 버퍼를 무조건 다 보낼 때까지 기다리면 느려지거나 응답 없는 클라이언트 때문에
  종료 자체가 멈출 수 있고, 그냥 버리면 방금 처리한 요청의 응답이 유실된다. non-blocking
  소켓에서 `Send_All()`을 **한 번만** 더 시도하는 최선 노력(best-effort) 방식은, 대부분의
  경우(작은 메시지, 커널 버퍼에 여유 있음) 실제로 성공하면서도 응답 없는 연결 때문에
  종료가 멈추는 일은 없다.

## v6 — Windows IOCP 기반 비동기 I/O 서버

- **IOCP는 준비 상태가 아니라 완료 결과를 전달한다.** `epoll`에서는 읽을 수 있다는 통지를
  받은 뒤 `recv()`를 호출하지만, IOCP에서는 `WSARecv()`를 먼저 게시하고 완료된 바이트 수를
  `GetQueuedCompletionStatus()`에서 받는다.

- **`AcceptEx()`의 0바이트 완료는 연결 종료가 아니다.** 초기 수신 길이를 0으로 지정한
  `AcceptEx()`는 정상 완료 시에도 전송 바이트가 0일 수 있다. 0바이트를 종료로 해석하는 규칙은
  Recv completion에만 적용하고 I/O 타입을 함께 확인해야 한다.

- **pending I/O보다 `OVERLAPPED` context가 오래 살아야 한다.** socket을 닫아 작업을
  취소해도 completion이 돌아오기 전에 context를 삭제하면 안 된다. 종료 시에는 socket을
  닫고, worker가 취소 completion을 회수해 context 목록이 빌 때까지 기다린 후 IOCP worker를
  종료해야 한다.

- **context만 살아 있다고 안전한 것이 아니라 OS에 넘긴 실제 버퍼도 completion까지 살아야
  한다.** Send context가 세션 송신 큐 내부 주소를 참조하면 종료 중 큐를 비울 때 포인터가
  무효화될 수 있다. 전송할 바이트를 Send context의 자체 버퍼에 복사하고 `WSABUF`가 그 버퍼를
  가리키게 하면 context와 데이터의 수명이 함께 보장된다.

- **세션과 I/O 작업의 수명은 분리할 수 있다.** 세션은 socket과 순서 보장 송신 큐를 소유하고,
  Accept/Recv/Send별 context가 각각 하나의 `OVERLAPPED` 작업만 소유하게 하면 Recv와 Send를
  동시에 진행하면서도 작업 완료까지 필요한 상태를 안전하게 유지할 수 있다.

- **completion의 `OVERLAPPED*`는 멤버 위치를 고려해 복원해야 한다.** 단순 포인터 변환은 첫
  멤버 배치에 의존하지만 `CONTAINING_RECORD`는 멤버 오프셋을 사용하므로 구조체 배치 변경에 안전하다.

- **partial send는 논리적 송신 범위와 실제 요청 범위를 구분해야 한다.** 세션의 송신 offset을
  완료 바이트만큼 이동하고 남은 범위로 새 Send context를 만들면, 수신 버퍼와 독립적으로
  continuation을 게시하면서 원래 메시지 순서를 유지할 수 있다.

- **worker의 종료 신호와 서버 상태는 역할이 다르다.** `Stopping` 상태는 후속 I/O 게시를
  막고, `PostQueuedCompletionStatus()`의 null `OVERLAPPED` 패킷은 pending completion을 모두
  처리한 worker를 실제 루프에서 빠져나오게 한다.

- **종료 요청과 자원 해제는 분리해야 공유 handle의 소유권이 명확해진다.** `Stop()`은 상태
  전환과 대기 스레드 알림만 담당하고, socket과 IOCP handle 정리는 `Clean_Up()` 한 곳에서
  수행하면 `Post_Accept()`와 종료 스레드가 `listen_socket`을 동시에 읽고 쓰는 경쟁을 피할 수 있다.

- **미리 게시한 Accept 개수는 성공 경로뿐 아니라 실패 경로에서도 보충해야 한다.** 실행 중
  실패한 `AcceptEx` context를 정리만 하면 accept depth가 하나씩 줄어든다. 종료 중 실패와
  실행 중 실패를 구분하고, 실행 중에는 대체 `AcceptEx`를 다시 게시해야 목표 depth가 유지된다.

## v7 — IOCP + game logic queue

- **TCP는 메시지 경계가 없는 바이트 스트림이라, Recv 한 번이 패킷 하나라는 보장이 없다.** 한 번의
  Recv에 패킷 여러 개가 붙어 오거나, 헤더 4바이트가 두 번의 Recv에 나뉘어 올 수 있다. 그래서 길이 헤더로
  경계를 직접 표시하고, 덜 모인 조각은 다음 Recv까지 들고 있어야 한다. 조립 버퍼를 Recv 함수의 지역
  변수로 두면 그 조각이 버려지고, 다음 Recv는 패킷 중간부터 읽게 되어 엉뚱한 값을 size로 해석한다.

- **동기화는 락이 아니라 구조로도 보장할 수 있다.** 세션마다 `WSARecv()`를 하나만 pending으로 두면 같은
  세션의 Recv completion은 동시에 처리될 수 없다. 그래서 세션의 조립 버퍼에는 mutex가 필요 없다. 반대로
  송신 큐는 completion worker와 logic 스레드가 모두 건드리므로 `send_mutex`가 필요하다.

- **이벤트의 순서는 "일어난 순서"가 아니라 "큐에 들어간 순서"로 정해진다.** `Post_Recv()`를 먼저 하고
  Enter를 나중에 넣으면, 그 사이에 다른 worker가 이 세션의 첫 패킷을 먼저 큐에 넣을 수 있다. 그러면
  logic 스레드는 아직 방에 없는 세션의 채팅으로 보고 버린다. 세션을 외부(I/O)에 공개하기 전에 Enter를 넣어야 한다.

- **경쟁 구간이 짧으면 일반 테스트로는 버그가 드러나지 않는다.** Enter 순서를 뒤집어도 500회 시도에서
  손실이 0건이었다. 두 줄 사이에 1ms 지연을 넣어 스레드 선점을 흉내 내자 500건이 전부 사라졌다.
  "테스트가 통과했다"는 것은 "버그가 없다"가 아니라 "이 조건에서는 안 드러났다"는 뜻이다.

- **logic 스레드를 하나로 두면 게임 상태에 락이 필요 없지만, 그 스레드가 곧 처리량의 상한이 된다.**
  200명 방송 부하에서 job 큐 최고 길이가 1997까지 올라갔다. v5에서는 reactor 하나가 병목이었고, v7에서는
  logic 하나가 병목이다. 병목은 없어지지 않고 자리를 옮긴다. 그래서 큐 길이처럼 병목을 볼 수 있는 지표를 남겨야 한다.

- **생산자와 소비자의 큐는 "가득 찼을 때 누가 기다리는가"까지 정해야 한다.** completion worker가 job 큐
  자리가 날 때까지 기다리면 IOCP 전체가 game 로직 속도에 묶인다. 그래서 `Push()`는 기다리지 않고
  실패를 돌려주도록 했다.

- **메모리 수명을 공유하는 것과 OS에 넘긴 버퍼의 수명은 따로 생각해야 한다.** 방송 패킷은
  `shared_ptr<const vector<char>>` 하나를 모든 세션이 공유해 복사를 줄였다. 하지만 `WSASend()`에 넘기는
  버퍼는 completion까지 살아 있어야 하므로 v6처럼 context 버퍼로 복사했다.

- **읽지 않는 클라이언트는 서버 메모리 문제다.** 서버가 보낼 데이터를 클라이언트가 가져가지 않으면 세션
  송신 큐에 계속 쌓인다. 상한을 없앤 빌드에서 60,000개 방송 후 작업 메모리가 7 MB에서 72 MB까지 늘었다.
  상한(4096개)을 둔 빌드는 해당 세션을 끊고 12 MB에서 멈췄다.

- **로그 출력도 공유 자원이고, 막힐 수 있다.** stdout이 파이프에 연결되어 있는데 아무도 읽지 않으면
  버퍼가 가득 찬 뒤 `std::cout`이 멈춘다. `Logging()`은 `log_mutex`를 쥔 채 출력하므로, 로그를 찍으려는
  completion worker와 logic 스레드가 줄줄이 같은 mutex에서 멈춰 서버 전체가 정지했다.

- **종료할 때는 일을 만드는 쪽부터 멈춘다.** logic 스레드는 송신 요청을 계속 만들어 내므로, I/O를
  정리하기 전에 job 큐를 닫고 logic 스레드를 먼저 join했다. 그 뒤 v6와 같은 I/O 취소와 drain을 수행한다.

- **`assert`는 Release 빌드에서 사라진다.** `NDEBUG`가 정의되면 `assert(조건)`은 아무 코드도 남기지 않는다.
  Release로 실행하는 테스트에서 `assert`만 쓰면, 조건이 틀려도 테스트가 항상 통과한다.

- **일을 다른 스레드로 넘기는 것이 항상 이득은 아니다.** logic 스레드의 `WSASend()`를 IOCP worker로
  넘기자 처리량이 오히려 약 30% 떨어졌다. 넘기는 데 드는 비용(큐 한 번 더, 공유 mutex 경쟁)이 넘겨서
  아끼는 비용보다 컸다. 반대로 "같은 일을 덜 하게" 만든 묶어 보내기(여러 패킷을 `WSASend()` 한 번에)는
  처리량을 약 3배 올렸다. 개선안은 감으로 고르지 말고, 하나씩 켜고 끄며 같은 부하로 측정해야 한다.

- **송신 중인 동안 쌓이는 큐가 곧 자연스러운 배치(batch)다.** 세션당 `WSASend()`를 하나만 진행시키면,
  그 송신이 끝나기를 기다리는 동안 쌓인 패킷을 다음 번에 한꺼번에 보낼 수 있다. 부하가 클수록 더 많이
  묶여서 시스템 호출 수가 줄어든다.

- **IOCP에서 backpressure는 "다음 Recv를 게시하지 않는 것"으로 만들 수 있다.** 서버가 읽지 않으면 TCP 수신
  버퍼가 차고, 흐름 제어로 클라이언트의 송신이 느려진다. 연결을 끊지 않고도 과부하를 상대에게 전달할 수
  있다. 다만 멈춘 세션을 누가 언제 깨우는지까지 설계해야 한다. 재개를 logic 스레드에만 맡기면, logic이
  이미 큐를 비우고 잠든 뒤에 멈춘 세션은 영원히 깨어나지 않는다.

- **재사용하는 context가 `shared_ptr`로 세션을 붙잡으면 순환 참조가 생긴다.** 세션이 context를 소유하고,
  pending 중인 context가 세션을 붙잡으면 서로를 놓지 못한다. completion 처리를 시작할 때 context의 세션
  참조를 꺼내(`std::move`) 끊어야, I/O가 모두 끝난 세션이 정상적으로 해제된다.

- **Windows에서 `QProcess::terminate()`는 콘솔 프로그램을 종료시키지 못한다.** Linux의 SIGTERM과 달리 창
  닫기 메시지를 보내는 방식이라, 창이 없는 콘솔 서버에는 전달되지 않는다. 서버가 정한 종료 방법(여기서는
  표준 입력의 Enter)을 그대로 사용해야 graceful shutdown이 실행된다.

- **다른 환경끼리 비교할 때는 같은 환경의 기준선을 함께 재야 한다.** v5(Linux)와 v7(Windows)의 왕복 지연만
  보면 v7이 훨씬 빨라 보였다. 같은 OS의 가장 단순한 echo 서버(v1, v6)를 함께 재자 차이 대부분이 OS와
  클라이언트 환경에서 온 것이고, 구조 때문에 더해지는 지연은 둘 다 수십 µs라는 것을 알 수 있었다.
  기준선이 없으면 환경 차이를 구조 차이로 잘못 읽는다.

- **패킷 단위로 일을 나누면 그만큼 고정 비용도 패킷 수만큼 든다.** v5는 Recv 한 번을 job 하나로 처리해서
  몰려 온 바이트가 저절로 묶이지만, v7은 게임 로직을 위해 패킷마다 job·할당·큐 잠금을 거친다. 그래서 작은
  패킷이 몰리면 v7의 처리량이 서버 쪽에서 먼저 막혔다. 정확한 단위로 나누는 것과 묶어서 처리하는 것은 서로
  균형을 잡아야 한다.

- **할당을 없애려고 버퍼를 고정하면 연결 수만큼 메모리가 늘어난다.** 세션마다 64 KiB 수신·송신 context를
  고정한 v7은 유휴 연결 1,000개에 133 MB를 썼다. 필요할 때만 버퍼를 잡는 v5는 3.6 MB였다. 속도와 메모리 중
  무엇을 아낄지는 예상 동시 접속 수를 보고 정해야 한다.

## v8 — 틱 기반 게임 루프 + 격자 AOI

- **틱 루프는 "일이 오면 깨어나는" 구조를 "정해진 시각에 깨어나는" 구조로 바꾼다.** v7 logic 스레드는 job 하나마다
  깨어났다. v8은 job이 와도 깨어나지 않고 다음 틱 시각까지 잔 뒤 쌓인 job을 한 번에 가져간다. 그래서 `Push()`는
  더 이상 `notify`하지 않고, 큐 잠금도 틱마다 한 번 소비자와 겹친다. 대신 입력이 처리될 때까지 최대 한 틱(50ms)을 기다린다.

- **다음 틱 시각은 "지금 + 주기"가 아니라 "예정 시각 + 주기"로 잡아야 지연이 쌓이지 않는다.** 103ms에 깨어났어도
  다음 틱은 150ms다. 지금 시각 기준으로 잡으면 깨어날 때마다 늦은 만큼 밀려 실제 주기가 50ms보다 길어진다.

- **늦은 틱은 따라잡을지 건너뛸지 정해야 한다.** 이미 느린 서버가 놓친 틱을 연달아 돌리면 더 느려진다. v8은
  건너뛰되 한 틱의 dt를 놓친 주기만큼 늘려, 이동 속도는 실제 시간 기준으로 유지했다.

- **시간을 직접 읽지 않는 코드는 테스트하기 쉽다.** `TickScheduler`가 `now()`를 부르지 않고 현재 시각을 인자로 받게
  하니, 가짜 시각만으로 "처리가 170ms 걸려 3주기를 놓친" 상황을 바로 재현할 수 있었다.

- **AOI의 핵심은 "누구에게 보낼지"를 줄이는 것이다.** 같은 500명에서 AOI를 끄면(셀 하나) 틱당 2.9 MB, 켜면 241 KB였다.
  전체 방송은 인원이 2배가 되면 전송량이 4배가 된다. 격자 AOI는 주변 인원에만 비례하므로 밀도가 같으면 인원에 선형이다.

- **시야 관계가 대칭이면 한 번의 계산으로 양쪽을 갱신할 수 있다.** "A가 B를 본다"와 "B가 A를 본다"는 항상 같이
  바뀐다. 셀을 넘는 플레이어 한 명만 기준으로, 새로 겹치게 된 셀과 더 이상 안 겹치는 셀만 훑으면 양쪽의 spawn/despawn이 나온다.

- **같은 틱 안의 여러 변경은 결과만 보내면 된다.** 같은 틱에 들어왔다 나간 대상은 +1과 -1이 상쇄되어 아무것도
  보내지 않는다. 클라이언트가 보는 것은 틱 사이의 상태 변화이지, 틱 안의 중간 과정이 아니다.

- **"정확하다"를 검증하려면 기대값을 클라이언트 밖에서 다시 계산해야 한다.** 봇이 받은 spawn/despawn만으로 주변
  목록을 재구성하고, 모두 멈춘 뒤 각 봇의 서버 위치로 격자 규칙을 다시 적용해 비교했다. 서버의 계산을 서버 코드로
  확인하면 같은 버그를 두 번 믿게 된다.

- **커널이 읽는 동안 버퍼가 살아 있어야 복사 없이 보낼 수 있다.** v8은 송신 큐의 버퍼를 `WSABUF` 배열로 직접
  가리킨다. 그런데 세션을 닫을 때 큐를 비우면, 아직 pending인 `WSASend()`가 읽는 버퍼가 해제될 수 있다. 그래서
  게시한 버퍼의 `shared_ptr`를 context의 `in_flight`에 completion까지 따로 붙잡아 두었다.

- **병목은 짐작하지 말고 단계별로 재야 한다.** 2,000명 틱이 86ms일 때 AOI 계산이 느릴 거라 생각했지만,
  틱을 입력/이동/수집/인코딩/송신으로 나눠 재 보니 대부분이 송신 게시였다. 로컬 연결의 `WSASend()`는 호출 안에서
  상대 버퍼까지 복사해 세션당 수십 µs가 걸렸다.

- **같은 "worker로 넘기기"도 넘기는 단위에 따라 결과가 반대가 된다.** v7은 채팅 메시지마다 넘겨서 30% 느려졌다.
  v8은 처음에 세션마다 넘겨 35 → 14ms, 게시가 필요한 세션을 worker 수만큼 묶어 넘기자 1,000명 5ms가 됐다.
  넘기는 비용은 횟수에 비례하고, 이득은 `WSASend()`를 여러 코어에 나누는 데서 나온다.

- **전역 잠금은 시스템 호출을 감싸는 순간 모든 스레드의 줄이 된다.** v7은 `WSARecv()`/`WSASend()`를 부르는 동안
  전역 `context_mutex`를 잡았다. v8은 pending I/O를 원자 카운터로만 세고, 종료 때 소켓을 닫아야 하는 Accept만 목록에 남겼다.
  마지막 I/O가 끝날 때만 잠그고 깨워서, 정리하는 쪽이 알림을 놓치지 않게 했다.

- **묶어 보내기에는 대가가 있다.** 한 틱 동안 받은 채팅을 틱 끝에 한 번에 돌려주니, 한 틱에 수 MB를 보낸
  클라이언트는 자기 송신 큐가 먼저 상한을 넘어 끊겼다. 메시지마다 보낼 때는 생기지 않던 문제다. 틱 구조에서는
  입력 속도 제한이 성능이 아니라 정상 동작의 조건이 된다.

- **부하 도구도 자원을 소모한다.** 봇이 먼저 연결을 끊으면 봇 쪽에 TIME_WAIT 소켓이 남아 임시 포트를 붙잡는다.
  측정을 몇 번 반복하자 1,436번째 연결에서 접속이 실패했다. 봇이 linger 0으로 바로 끊게 해 해결했다.

- **바이트를 줄이는 일에도 CPU 비용이 든다.** 좌표를 16비트로 줄여 틱당 송신량을 3.7 → 2.5 MB로 줄였지만, 처음에는
  항목마다 나눗셈과 `std::round`를 써서 2,000명 인코딩이 2.6 → 6ms로 늘었다. 배율은 목록마다 한 번 계산하고
  반올림은 `+0.5` 뒤 정수 변환으로 바꾸어 3.5ms로 되돌렸다. 줄인 바이트와 늘어난 계산을 같이 봐야 한다.

- **양쪽이 같은 값을 계산하려면 식도 같은 순서로 해야 한다.** 봇은 받은 16비트 좌표를 서버 좌표와 정확히 비교한다.
  서버 인코딩과 검증 코드가 조금이라도 다른 식(나눗셈 vs 곱셈)을 쓰면 float 반올림 차이로 몇 개가 어긋날 수 있다.
  그래서 인코딩도 `Quantize_Coordinate`와 같은 식을 그대로 거치게 했다.

- **입력 순번은 "서버가 무엇을 반영했는지"를 클라이언트에게 알려 주는 최소한의 장치다.** 서버 권위 구조에서
  클라이언트가 서버 위치를 기다리면 50ms 이상 늦게 움직인다. `S_SelfState`에 마지막으로 반영한 입력 순번을 붙이면,
  클라이언트가 먼저 예측해 움직이고 서버 위치가 오면 그 입력까지 반영된 결과와 비교해 보정할 수 있다.

  (2026-11-22) 위 세 항목은 셸 heredoc으로 쓰면서 한글이 깨진 채 커밋됐던 것을, 남은 글자와 맥락으로 다시 썼다.
  숫자와 코드 이름은 원래 그대로이고, 문장은 뜻을 살려 복원한 것이라 원문과 조사·어미가 조금 다를 수 있다.

## v9 — v8 틱 서버의 Linux(epoll) 이식

- **IOCP는 "끝났다"를, epoll은 "이제 해도 된다"를 알려 준다.** IOCP는 버퍼를 미리 맡기면 커널이 읽기·쓰기를 끝낸 뒤
  알려 준다(완료 통지). epoll은 읽거나 쓸 수 있게 됐다는 것만 알려 주고 `recv`/`send`는 직접 부른다(준비 통지).
  그래서 epoll 쪽에서는 `EAGAIN`, 일부만 보낸 상태, 남은 바이트를 서버가 직접 관리해야 한다. 같은 게임 로직이 위에 올라가도
  네트워크 계층의 책임이 달라진다.

- **LT(level-triggered)는 "아직 남아 있으면 또 알려 준다", ET(edge-triggered)는 "바뀌었을 때 한 번만 알려 준다".**
  LT에서는 fd당 몇 번만 읽고 넘어가도 남은 데이터를 다음 `epoll_wait`가 다시 알려 줘서 한 연결이 reactor를 독차지하지 않는다.
  ET에서 그렇게 하면 남은 데이터가 영영 알려지지 않아 연결이 멈춘 것처럼 보인다.

- **LT에서 `EPOLLOUT`은 필요할 때만 켜야 한다.** 송신 버퍼는 거의 항상 비어 있어서, 켜 두면 보낼 것이 없어도 매번 깨어난다.
  다 못 보냈을 때(EAGAIN) 켜고, 큐를 다 비우면 끈다.

- **fd 번호는 바로 재사용된다.** 연결을 닫으면 그 번호가 다음 `accept`에 다시 나온다. 같은 `epoll_wait` 묶음에 닫힌 연결의
  이벤트가 남아 있으면, fd로 세션을 찾는 순간 새 연결에 옛 이벤트가 적용된다. 그래서 epoll에 넣는 키는 계속 증가하는
  session_id로 했다. v8에서 socket 핸들 대신 session_id를 게임 로직에 쓴 것과 같은 이유다.

- **끊긴 연결에 쓰면 프로세스가 죽을 수 있다.** Linux는 상대가 닫은 소켓에 쓰면 SIGPIPE를 보내고 기본 동작이 프로세스 종료다.
  `send`/`sendmsg`에 `MSG_NOSIGNAL`을 주면 시그널 대신 `EPIPE` 오류로 받는다. Windows에는 없던 문제다.

- **다른 스레드를 깨우는 데는 eventfd 하나면 충분하다.** 틱 스레드는 "보낼 세션 목록"을 mutex로 넘기고 eventfd에 1을 쓴다.
  여러 번 써도 값이 더해질 뿐이라 reactor는 한 번 깨어나 모아서 처리한다. 종료 요청도 같은 eventfd를 쓴다.

- **시그널은 핸들러 대신 `sigwait`로 받으면 평범한 코드에서 처리할 수 있다.** 모든 스레드에서 SIGINT/SIGTERM을 막고(스레드를
  만들기 전에 막아야 물려받는다) main 스레드가 `sigwait`로 기다리면, 받은 뒤 `Stop()`처럼 mutex를 쓰는 함수를 안전하게 부를 수 있다.

- **흐름 제어는 "언제 판단하느냐"에 따라 걸리기도 하고 안 걸리기도 한다.** 처음에는 준비된 fd들을 다 읽은 뒤 수위를 봐서,
  수위 200에서도 큐가 2,239까지 올라가며 사실상 아무것도 막지 않았다. 읽기 전에 판단하게 바꾸자 이번에는 정말로 틱당 약 200개만
  받아들였다. 그래서 처음엔 "고쳤더니 처리량이 줄었다"처럼 보였는데, 그게 수위가 의도대로 동작한 모습이었다. 시험 수위는 부하와
  비슷하게(1,000/250) 따로 잡아야 "넘침이 줄었는지"를 볼 수 있다.

- **미룰 때는 순서까지 같이 미뤄야 한다.** 입장·퇴장이 몰릴 때 그것만 다음 틱으로 미루면, 아직 입장하지 않은 세션의 패킷이 먼저
  처리돼 버려진다(v7의 "Enter보다 먼저 온 채팅" 문제와 같다). 상한에 닿으면 그 뒤의 job을 패킷까지 도착 순서 그대로 미뤘다.

- **N²은 이동만이 아니라 입장·퇴장에도 숨어 있다.** 격자 AOI는 이동 비용을 주변 인원으로 묶지만, 한 시야 안에 N명이 몰린 상태에서
  모두가 한꺼번에 들어오거나 나가면 보임/사라짐 기록이 N²이 된다. 퇴장만 고치고 다시 재 보니 입장에서 같은 일이 났다.

- **같은 입력을 두 컴파일러에서 재현하려면 표준이 값을 정한 것만 써야 한다.** `std::mt19937`의 출력은 표준이 정하지만
  `uniform_real_distribution`과 `cos`/`sin`의 결과는 구현마다 다르다. 원값과 고정 상수로 입력을 만들자 g++와 MSVC가 같은 일을 했다.
  결과 비교도 `unordered_map` 순회 순서처럼 구현마다 다른 것에 기대지 않는 값(개수, 합)으로 해야 한다.

- **API를 바꿨는데 빨라졌다고 API 덕분은 아니다.** v9의 2,000명 틱 시간은 v8의 약 1/2.5~1/3이었지만, 두 버전 모두 틱 스레드는
  소켓을 만지지 않는다. 바뀐 것은 컴파일러, 메모리 할당기, 실행 환경이다. 측정값의 차이를 설명하려면 무엇이 같고 무엇이
  달랐는지부터 적어야 한다.
  나중에 게임 로직만 따로 재 보니(2026-11-23) 컴파일러·표준 라이브러리 몫은 약 1.6배(약 2ms)였고, 서버 틱 차이 약 9ms의 나머지는
  서버 구조와 실행 환경 쪽이었다. "API 덕분이 아니다"도 재기 전에는 추측이었다. 의심이 들면 나눠서 재야 한다.

## v10 — io_uring 기반 완료 통지 서버

- **io_uring은 Linux의 IOCP다.** 작업을 제출 큐(SQE)에 넣고 결과를 완료 큐(CQE)에서 받는다. 그래서 v8에서 겪은 문제가 그대로 돌아왔다.
  커널이 버퍼를 쓰는 동안 그 버퍼(수신 버퍼, 송신 iovec, msghdr)가 살아 있어야 하고, 세션을 닫으려면 진행 중인 작업을 취소하고 그 완료가
  모두 돌아온 뒤에야 fd를 닫을 수 있다. epoll(v9)에는 없던 걱정이다.

- **완료 큐에는 포인터 대신 "누구의 무슨 작업인지"를 담는다.** user_data를 세션 포인터로 하면 세션을 지운 뒤 늦게 온 완료가 해제된 메모리를 가리킨다.
  (작업 종류, session_id)를 담고 목록에서 찾으면, 이미 없는 세션의 완료는 그냥 무시할 수 있다. v9에서 fd 대신 session_id를 키로 쓴 것과 같은 생각이다.

- **multishot은 "한 번 걸면 계속 온다".** accept와 recv를 한 번 걸어 두면 접속·데이터마다 CQE가 온다. 끝났는지는 `IORING_CQE_F_MORE`로 안다.
  그래서 진행 중 작업 수는 SQE마다 늘리고, F_MORE가 꺼진 마지막 CQE에서만 줄여야 한다.

- **시스템 호출을 줄이는 것과 CPU를 줄이는 것은 다르다.** 시스템 호출은 약 1/7.6로 줄었지만 I/O 스레드 CPU는 10~15%만 줄었다.
  데이터 복사와 커널 안의 네트워크 처리는 그대로 남는다. 틱 시간은 같았다(게임 로직이 같다).

- **버퍼를 누가 갖느냐가 메모리를 정한다.** 세션마다 버퍼를 들면(fixed, IOCP 방식) 연결 수에 비례하고, 커널이 공용 묶음에서 골라 쓰게 하면
  (provided buffer ring) 연결 수와 상관없다. 대신 묶음이 모자라면 `-ENOBUFS`로 끝나 다시 걸어야 한다.

- **완료 통지에서는 "읽기 전에" 흐름 제어를 할 수 없다.** v9는 읽기 전에 수위를 보고 멈췄지만, io_uring은 커널이 이미 받아 온 뒤에 알려 준다.
  받은 데이터는 처리해야 하므로 수위를 넘는 양이 더 크다.

- **시간을 잴 때는 단조 시계를 쓴다.** 시험이 벽시계(`time.time()`)로 "5초 동안 이동"을 쟀는데, WSL2가 벽시계를 조정해 실제로는 6초가 됐다.
  서버는 `steady_clock`이라 정확히 움직였고, 시험만 틀렸다. 처음엔 v10 버그인 줄 알았는데 v9에서도 같은 비율로 실패해 시험 쪽임을 알았다.

- **넘침의 원인은 "넘을 때"가 아니라 "다시 열 때"에 있었다.** 수위를 넘은 순간 이미 받아 온 데이터를 의심해 세션 조립기에 쌓아 두게
  바꿨는데, 넘침이 그대로였다. 실제로는 큐가 비었을 때 멈춘 세션 수천 개를 한꺼번에 재개하면서 쌓아 둔 패킷을 수위 확인 없이 넣고
  있었다. 문을 닫는 조건만큼 여는 쪽에도 같은 조건이 필요하다. 그리고 누적 최대값처럼 다른 사건(처음 접속)이 섞이는 지표로는 원인을
  가를 수 없어, 구간별 최대를 따로 만들어야 했다.

- **버퍼 묶음은 크기보다 개수가 중요하다.** 공용 버퍼가 바닥나는 것은 커널이 "데이터가 온 연결 수만큼" 버퍼를 동시에 원하기 때문이다.
  같은 메모리라도 작게 많이 쪼개면(4 KiB × 1,024 → 1 KiB × 4,096) 바닥나지 않았다. 패킷이 작은 프로토콜이라 가능한 선택이다.

- **SQPOLL은 시스템 호출을 없애는 대신 코어 하나를 쓴다.** ring 스레드 CPU는 37% → 5%로 줄었지만 커널 스레드가 99%를 써서 전체는
  늘었다. 지연을 아주 낮춰야 하고 코어가 남는 경우에 맞는 선택이지, 이 서버처럼 20Hz로 묶어 보내는 구조에서는 이득이 없다.

- **최적화 옵션은 켜기 전에 잰다.** 고정 파일은 이름만 보면 빨라질 것 같지만 이 부하에서는 차이가 없었다. fd를 찾는 비용보다 데이터 복사와
  네트워크 처리 비용이 훨씬 크기 때문이다.
